# IHC System — Agent Notes

No build, no tests, no lint, no CI. Plain XAMPP (Apache + PHP + MySQL) + a Node email/SMS reminder service.

## Run

- Frontend: static files, no bundler. Entry is `log in.html` (note the space — quote paths, URL-encode as `%20`):
  `http://localhost/ihc-system/log%20in.html`
- PHP APIs need XAMPP Apache + MySQL with DB `ihc` (credentials `root`/empty are hardcoded in each PHP file). Base: `http://localhost/ihc-system`
- Node service (from `backend/` only): `npm install` then `npm start` (port 3000). Config comes from `backend/.env` — never commit it, never print secrets. `server.js` prints MySQL/SMTP/SMS diagnosis on boot; trust that output.
- One-off reminder check (from `backend/`): `npm run reminders:run`

## Architecture: two halves share MySQL `ihc`; login is DB-verified, sessions are client-side

- `html/` + `js/` + `css/` = role dashboards (admin / clerk / client). Login (`js/log in.js`) POSTs `{email,password}` to `php/api_auth.php`, which verifies ALL roles against MySQL: admin/clerk against `ihc.officers` (bcrypt `password_hash`, seeded by `backend/migrations/004_staff_accounts_ihc.sql` — demo logins `admin@ihc.com/admin123`, `ana|mark|jessica@ihc.com/clerk123` → officers 1(admin)|2|3|4), clients against `ihc.client_accounts` (migration 003, one row per email, multi-contract emails are rejected with a billing message). If the server is unreachable OR rejects, the script falls back to `js/portal-store.js` localStorage demo seeds so the advertised demo client credentials still work. The session is still the shared `IHC_USER` localStorage key on the XAMPP origin — there are no server sessions, and the clerk dashboard's old no-session demo backdoor was removed (it now redirects to login). Don't add endpoint session guards without asking.
- `php/installment-schedule.php` is the ONE place that turns a `contracts` row + its `payments` rows into an installment schedule (`ihc_schedule()`): discount is applied once to net TCP, downpayment at start_date, equal amortizations at +1..n months (last absorbs rounding), payments allocated chronologically, a partially covered installment keeping its balance, and the first uncovered row as `next`. All dashboard/payment/SOA consumers `require_once` it. It is pure functions (no PDO, no output): change allocation rules HERE, never inside one endpoint, or the dashboards will disagree again.
- `php/api_admin.php` feeds the admin dashboard live data (it used to render 12 hardcoded mock contracts): GET `?action=overview` → ledger rows + contracts register + notifications log + KPIs + cash-flow actuals; GET `?action=schedule&contractId=IHC-<n>` → installment schedule (downpayment at start_date, amortizations at +1..n months, posted payments allocated chronologically). Ledger rows describe the contract's **next payment** (`paymentType` `Downpayment` / `Installment Payment #n` / `Settled in Full`, `amount` = still due on it, `dueDate` = its due date, `status` derived from it) so they match the clerk ledger exactly; `outstanding` is the net whole-contract principal balance (the formal SOA adds as-of interest/penalty, reservation fees, additional equity, and charges for its richer TOTAL DUE). Admin stays view-only for contract payments — it sends reminders and prints SOAs, it never inserts into `payments` (only `php/post-payment.php` does). It folds `payments.contract_id` (`CON-<id>`, bare `7`, `IHC-14`) onto integer contract ids in PHP — never SQL-JOIN payments/notifications against contracts (mixed collations blow up; see the ack bullet below).
- `php/api_soa.php` + `php/soa-builder.php` are the canonical, database-driven SOA path used by Clerk, Admin, and Client (`js/soa.js` + `css/soa.css`). The document combines `ihc_schedule()`, payment allocations/ORs, reservation fees, `additional_equity_payments`, `additional_charges`, configurable `soa_settings`, and contract financing/property fields. Admin edits SOA settings and records additional charges from its dashboard. Interest/penalty shown on an SOA is an as-of-date calculation for the first uncovered overdue row; the configured/global rate is in `soa_settings.penalty_rate_percent` and contract overrides are snapshotted on `contracts`.
- Payment posting through `php/post-payment.php` is the only regular-payment writer. It locks the contract, revalidates the current SOA/installment, generates the automatic OR, stores the actual cash amount plus optional `check_number` / `external_reference` / `receipt_requested` (migration 010), and writes `payment_allocations` in the same transaction. `ihc_schedule()` applies only each allocation's `principal_amount`; overpayment is recorded separately in `additional_equity_payments`, so cash collections do not reduce the principal schedule twice. The Clerk can apply only the current installment or auto-advance the oldest unpaid rows, and sends expected SOA/installment values to reject stale forms. The formal SOA replays payments/allocation-aware principal amounts for backward compatibility with legacy rows.
- `php/api_dashboard.php` (GET `?officerId=`) is the live clerk-dashboard endpoint. It runs the shared `ihc_schedule()` from `php/installment-schedule.php` and returns the contract's next payment: `nextType` (`downpayment` | `installment` | `settled`) + `nextInstallmentNo` (null for the downpayment) drive the row's `Installment Payment #n` label and the Payments queues — label and queue filters in `clerk-dashboard.html` must stay in sync with those values. `php/api_dashboard1.php` and `php/api_insert.php` are dead legacy — nothing references them, and `api_dashboard1.php` requires a nonexistent `../db.php`. Leave them alone.
- `backend/db.php` is NOT a shared DB include — it is the POST-only New-Contract handler (405s on GET). Dashboard/payment PHP files connect with their own inline PDO; don't consolidate them into `require db.php`. It persists **every field the New Contract form collects**: the base contract columns, financing (`dp_mode` / `dp_terms` / `bank_name` / `annual_interest_rate`), formal SOA terms (discount/loan/equity/property/client-address fields), the bcrypt `client_accounts` upsert and `officer_id` — contract + account in ONE transaction. Validation mirrors the form (monthly downpayment ⇒ 1–60 month deposit term, bank/rate required, optional SOA amounts/rates bounded), and the response echoes the stored financing values for the clerk mirror.
- `php/api_holding_fees.php` is the **legacy** officer-scoped Holding Fees path (`GET ?officerId=` → rows, `POST {action:'save', ...}` → `holding_fees` with `proof_data_url` base64). It is kept for back-compat but is superseded.
- `php/api_bank_rates.php` serves the **editable per-bank default annual interest** (§20, admin dashboard "Financing Banks" card; picked up by the clerk New Contract form's bank `<select>` + auto-fill). `bank_rates` (`bank_name`/`annual_rate`/`display_label`/`sort_order`) self-heals on first use (`CREATE TABLE IF NOT EXISTS` + `INSERT IGNORE` seeds); `migrations/007_bank_rates_ihc.sql` seeds it for fresh DBs. `GET ?action=list` (clerk + admin) and `POST {action:'update', rates:[{bank,label,rate}]}` (validates bank non-empty, rate 0–100, upserts). The rate is snapshotted onto each contract at creation, so edits only affect NEW contracts. The shared ledger schedule still uses equal principal splits and does not post interest; the client offline model and formal SOA may display/configure interest separately, but do not change ledger allocation without an explicit finance decision.
- `php/api_holding_reservation.php` is the **current Holding & Reservation service** (`php/api_holding_reservation.php:31` `ensureHoldingTables()` self-heals `property_units` + `holding_fees` + `reservation_fees` + `audit_logs` + `business_rules` even if `migrations/005`/`006` not yet run — see `backend/migrations/006_holding_fees_upgrade_legacy.sql` for the `ALTER TABLE` upgrade of the legacy `holding_fees` schema, including `proof_data_url` → `proof_path` file migration). Contract-hold linkage is `property_units.display_label` (unique, backfilled from `contracts.property_address`) with `status` `AVAILABLE → ON HOLD → RESERVED → SOLD` (§13). `holding_fees` (`PENDING/PAID/EXPIRED/REFUNDED/FORFEITED/CONVERTED/CANCELLED` + `start_date`/`expiration_date` default +30d via `business_rules.holding_fee.default_days`, `reference_number`/`or_number` per §14 `PENDING` → `Pending`/`Not Yet Issued` vs `PAID` → required) and `reservation_fees` (`PENDING/PAID/CANCELLED/REFUNDED` + optional `holding_fee_id` link, `PAID` auto-marks linked holding `CONVERTED` when `business_rules.holding_fee.convert_on_reservation=1`). All inserts use `SELECT ... FOR UPDATE` on `property_units` inside a transaction so concurrent holds cannot double-book; refundability (`business_rules.refundable`, `allow_direct_reservation`) is checked before `REFUNDED`/direct-reservation transitions. `GET ?action=dashboard_summary|holding_fees|reservation_fees|payment_history|property_unit|business_rules|audit_logs` and `POST create/update_holding_fee|create/update_reservation_fee|update_holding_status|update_reservation_status|unit_status_update|expire_sweep|business_rules_update` (`unit_status_update` moves a unit `AVAILABLE → ON HOLD → RESERVED → SOLD` manually and refuses to un-sell a `SOLD` unit; `business_rules_update` only writes the 6 known policy keys) — clerk uses `HOLDING_API = API_BASE + '/php/api_holding_reservation.php'` (moved to the top of `DOMContentLoaded` so `loadDashboard()` can read it). Admin overview `php/api_admin.php:257` exposes the same `holdingSummary`/`expiringHolds` for the new dashboard widgets. Legacy table `officer_id`/`proof_data_url` columns are retained read-only (migrated to files on first `GET` when needed) so existing `holding_fees` rows keep working.
- Client ↔ clerk link is server-side only (never cross-browser localStorage): `php/api_client.php` (`ledger` for contract+payments+**`schedule`**+**`totals`**+notifications; `lookup` still verifies email+password but login now goes through `api_auth.php`). The `schedule` array is the shared `ihc_schedule()` output (paid/paidAmount/payDate/orNumber/status per installment) and is the client's SOURCE OF TRUTH: `client-dashboard.html` replaces its localStorage projection with it on load (`applyServerSchedule`) and KPIs come from `totals.paid` + the schedule rows. Local storage is now purely the offline fallback (and the local `buildSchedules()` interest-bearing model only renders when the server is unreachable). Merge stays idempotent via `syncedPaymentIds` / `srvLogId`. Client portal accounts live in `ihc.client_accounts` (bcrypt `password_hash`, one row per email): `backend/db.php` upserts them on New-Contract POST (`accountAction` = created/updated). Contracts enrolled before that feature have no account row yet — provision one via `php/api_portal_account.php`. Still no server sessions; replace pre-production.

## PHP ↔ Node contract (don't break)

- Hardcoded bases: PHP at `http://localhost/ihc-system`, Node at `http://localhost:3000` (`127.0.0.1:3000` from PHP). Manual Clerk reminders first fetch `php/api_soa.php?action=summary&contractId=...` (a whitelisted compact payload), then call `POST /api/contracts/<id>/send-reminder` with `recipientEmail`, `recipientPhone`, and `soaSummary`; when the current row has a matching posted payment, the Clerk also sends its `paymentId` so PHP returns the exact transaction context instead of relying on the next-row label. `backend/emailService.js` normalizes that summary again and never emails detailed schedule rows/allocations/signatures. `backend/db.php` and `php/post-payment.php` → reminder/receipt routes. Mail is best-effort after ledger writes; the send-reminder route treats each channel independently and succeeds when email OR SMS delivers.
- `officer_id` is VARCHAR (can be `DEMO-001`) — never `(int)`-cast it. `payments.contract_id` stores the prefixed string (`CON-<id>`); `post-payment.php` extracts the trailing digits to verify against `contracts.id`.
- `docs/daily-reminder-automation.md` is the authoritative reminder runbook; `docs/reminder-email-prompt.md §6` is partly stale (it describes an `ihc_cms` schema and `001_init_schema.sql` flow the live code doesn't use — `cronJobs.js` now asks `php/api_soa.php?action=reminder_queue` for the canonical next schedule row, then applies per-channel dedup in `notifications_logs`).

## Reminders: pick ONE scheduler

- Windows Task Scheduler → `run-reminders.js` daily 8:00 AM Asia/Manila (Start in: `backend/`, args: `run-reminders.js`), OR in-process cron via `ENABLE_IN_PROCESS_CRON=true` + long-running `npm start`. Never both — double sends.
- Dedup lives in `notifications_logs` and is PER CHANNEL (`email` vs `sms`): `due_soon` is sent once per contract/channel/due date (so a downpayment notice cannot suppress a later installment), while `overdue` is once per day. Schema needs `migrations/002_reminder_automation_ihc.sql` applied to `ihc` (`CREATE TABLE` in `create_notification_logs.sql` is the fallback for fresh DBs).
- SMS reminders use Semaphore (semaphore.co, PH gateway, ~PHP 0.56/text) via `backend/smsService.js`: needs `SEMAPHORE_API_KEY` in `backend/.env`, plus `SEMAPHORE_SENDER_NAME` when the account has no default Sender Name (blank key = SMS channel silently skipped, email unaffected; plain `fetch`, no npm dep). Phone comes from `contracts.cellphone_number` (validated to E.164, sent as `09XXXXXXXXX`); SMS logs store the number in `client_email` (no phone column) with `channel='sms'`. Currently `due_soon` only — overdue is email-only.
- `ACKNOWLEDGEMENT_SECRET` must be set (long random) or ack links throw; email `Open Client Dashboard` / ack URLs default to localhost — override `CLIENT_LOGIN_URL` / `CLIENT_DASHBOARD_URL` / `ACKNOWLEDGEMENT_URL` in `.env` when deployed.
- Holding fee lifecycle: `holding_fees.status` → `EXPIRED` automatically via `php/api_holding_reservation.php:127` `expireStaleHolds()` (lazy on every `GET` + `cronJobs.js:163` `runHoldingFeeExpiration()` daily 12:05 AM `Asia/Manila`) when `expiration_date < CURDATE()` and `converted_to_reservation_id IS NULL`; if `business_rules.holding_fee.expire_makes_available=1` the `property_units` row flips `ON HOLD → AVAILABLE` (audited, never deleted). `holding_expiring` notices (2 days before expiry) are sent like payment reminders via `php/api_holding_reservation.php` / `cronJobs.js:fetchHoldingExpiringRows()` — `due_soon` per-channel dedup applies (`reminder_type='holding_expiring'` in `notifications_logs`, `channel='email'/'sms'`), client gets `Hi {name}, ... HF-{id} ({unit}) expires...` and clerk sees the `Expiring Holds` table (sorted nearest first) + `ACTIVE HOLDS` KPI.
- Ack signal is a transient modal only: clerk dashboard polls `GET /api/acknowledgments/recent?officerId=&since=` (local wall-clock `YYYY-MM-DD HH:mm:ss`, cursor in `localStorage`) every 5 min and pops one confirm modal per new `ack_email` row. No ack column/KPI/badges on the dashboard. SQL joining `notifications_logs.contract_id` to `contracts.id` needs explicit `COLLATE utf8mb4_general_ci` (mixed collations error at runtime).

- **"Still unpaid" account count + server-side report filters** (`api_admin.php?action=dues`, `js/dues-report.js`). The "Still unpaid" card shows the account count next to the money: `totals.stillUnpaidCount` = unique accounts with an unpaid balance (the accounts the `stillUnpaid` money belongs to) and `totals.unpaidAccountCount` = unique accounts listed in the table; both are also returned per clerk (`clerks[].stillUnpaidCount`). Accounts are keyed by contract id (`C:<id>`), so an account is never counted twice even when several installments or workbook months land on it. The card renders the count as an understated pill ("N accounts with an unpaid balance" — N is the balance count, the accounts the money belongs to) **plus** a second line ("N in the Clients due list • M owing only from earlier periods"), so the two numbers are never confused: the pill counts every account that still owes, the second line counts the accounts listed in the "Clients due" table (e.g. 308 with a balance vs 170 listed this week; the 138 others owe only from earlier periods, and ticking "include overdue from earlier" brings the list up to the same 308). Workbook months (`legacy_month_snapshots`) have no payment history, so they are skipped when `perf` is set, and their phase is resolved through the account.
